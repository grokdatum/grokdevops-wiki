## Hint 2
🎯 HINT 2: Understanding Volume Permissions

The problem is the volume ownership doesn't match the container user!

📚 How Volume Permissions Work:

**Default Behavior:**
- Volumes are owned by root (user 0, group 0)
- Container runs as user 1000
- User 1000 can't write to root-owned directory!

**Container Security Context:**
```yaml
containers:
- securityContext:
    runAsUser: 1000    # Container runs as this user
    runAsGroup: 1000   # Container runs as this group
```

**Pod Security Context with fsGroup:**
```yaml
spec:
  securityContext:
    fsGroup: 1000  # ✅ Changes volume ownership to group 1000!
```

🔍 How fsGroup Works:

1. Volume is mounted
2. Kubernetes changes ownership: `chown -R :1000 /volume`
3. Volume group = 1000
4. User 1000 (in group 1000) can now write!

**Without fsGroup:**
```bash
drwxr-xr-x  2 root root  4096 /data  # User 1000 can't write
```

**With fsGroup: 1000:**
```bash
drwxrwsr-x  2 root 1000  4096 /data  # Group 1000 can write!
```

💡 The Solution:
Add fsGroup to pod's securityContext:
```yaml
spec:
  securityContext:
    fsGroup: 1000  # Match runAsGroup
```

💡 Action: Set fsGroup in the pod spec's securityContext!

## Hint 3
✅ HINT 3: Complete Solution

Fix: Add fsGroup to pod securityContext

📝 In Pod spec:
```yaml
apiVersion: v1
kind: Pod
metadata:
  name: writer-app
spec:
  securityContext:  # ✅ Add at pod level!
    fsGroup: 1000
  containers:
  - name: app
    securityContext:  # Container level
      runAsUser: 1000
      runAsGroup: 1000
    volumeMounts:
    - name: data
      mountPath: /data
```

🔑 Key Points:
- fsGroup goes in **spec.securityContext** (pod level)
- runAsUser goes in **containers.securityContext** (container level)
- fsGroup should match runAsGroup for proper permissions

🚀 Apply:
```bash
kubectl delete -f broken.yaml
kubectl apply -f solution.yaml
kubectl logs writer-app -n k8squest
# Should show "Write successful!"
```

🔍 Verify permissions:
```bash
kubectl exec writer-app -n k8squest -- ls -la /data
# Should show group ownership as 1000
```

💡 Remember: fsGroup changes volume group ownership so the container user can write!
